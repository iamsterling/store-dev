# B — Bird two-way email: product contracts and decision gates

## Decision and evidence status

**Verdict: CONDITIONAL candidate for a controlled two-way email pilot; NO-GO for a claim of automatically recoverable, duplicate-free uncertain sends.** Current primary documentation describes enough inbound storage and HTTP API control to keep business identities, durable history, routing and workflow in Supabase. It does **not** establish that send execution and idempotency persistence are atomic. In fact, its detailed failure contract explicitly permits re-execution after a side effect. Bird preference is reasonable only if this limitation is accepted through a fail-closed uncertainty queue, or Bird supplies a stronger email-specific contract and the account passes the tests below.

Owner: workstream B. Research-only; no account access, DNS changes, endpoint registration, sandbox sends, paid resources, production or code edits. All capabilities below are **documented**, not runtime-tested. Architectural consequences are labelled **inference/proposed**. Confidence is high in the cited text, moderate in current product/account availability, and low in untested end-to-end behavior.

Access session: 2026-10-15 environment date; shared ledger labels the research wave 2026-10-16 UTC. Citations use access date **2026-10-15** rather than inventing a later observation. Most pages expose no publication/update date. `/v1` is an API version, not a documentation publication date. Public OpenAPI identifies itself as Bird API **1.0.0** (bounded HTTP extraction); this is not proof of deployed server version.

Decision frame: (1) choose the exact email surface, (2) capture complete inbound artifacts and correct reply semantics, (3) authenticate and recover ingress, (4) reconcile uncertain outbound side effects, (5) establish provisioning/permissions/limits. Do not choose based on speculative future channels. H1: current Bird email can meet all gates; H2: SparkPost is needed; H3: another provider is safer. Distinguishing observations: raw-MIME retrieval and recovery windows; email-specific atomic idempotency; account entitlement to the documented surface.

## 3. Provisioning, credentials and identities

Current Bird organizations choose `us1` or `eu1` at signup; region is immutable in v1. Workspace/message/event data is documented as region-local; global authentication/admin data is separate. Keys must match host or receive `421`; no global data-plane URL (B01, B12). This is a vendor residency statement, not a legal or infrastructure audit.

Service keys are workspace-scoped. Create through dashboard or a human CLI OAuth grant with `api_keys:write`; API keys cannot issue more keys, manage billing or organization members. Secret shown once; optional expiry; rotation replaces a key with a default 24-hour overlap, does not carry expiry, and inherits source IP restrictions. Exact IP-allowlist creation syntax was not established. Suggested separation (**proposed**): send worker `emails:write`; reconciler read-only email/inbound permissions after entitlement verification; separate `webhooks:read` monitoring; human-controlled `domains:write` / `webhooks:write` provisioning. Do not give an agent unrestricted provider credentials simply because Bird calls it an agent SDK. Scoped send permission is not recipient/address-specific business authorization (B12).

Domain setup: `POST /v1/email/domains`, publish returned DNS records, `POST /v1/email/domains/{domain_id}/verify`. Domain `status: verified` proves DKIM ownership; sending gate `capabilities.sending` additionally requires return-path CNAME and DMARC. Use a dedicated subdomain to avoid capturing corporate/apex MX. Enabling receiving requires DKIM verification and available receiving registration; it captures **any local-part** at that domain. Same sending domain may register in multiple organizations with separate DKIM keys, but receiving cannot collide across organizations. Do not copy legacy SparkPost MX values into new Bird setup: use the returned records (B04, B22).

No-DNS receiving alternative: `POST /v1/email/inbound-addresses` generates a fixed random `@{region}.inbound.bird.com` forwarding address. Existing mail provider forwards there. This is not an arbitrary custom sender identity and forwarding can affect sender authentication. Own-domain mailbox forwarding is another optional product, not necessary to the direct API design (B04, B23).

Current send allows verified-domain From and recipient address arrays without creating contacts. The shared onboarding sender reaches only verified workspace members or sandbox addresses; 50 recipients/organization/UTC day, including sandbox. It is not evidence of arbitrary production-recipient availability before domain verification (B02, B24).

## 4. Receive and reply contract

### Endpoint inventory

- `GET /v1/email/inbound-messages`: workspace-wide cursor list; filters `from` (lowercase exact), `inbound_address_id`, `mailbox_id`, `received_after`, `received_before`; `starting_after`, `ending_before`, `refresh_cursor` support paging/refresh (B05).
- `GET /v1/email/inbound-messages/{inbound_message_id}`: parsed addressing, subject, RFC `message_id`, `in_reply_to`, optional `references`, authentication fields, attachment manifest (B04–B05).
- `GET .../{id}/body`: original parsed HTML/plain text.
- `GET .../{id}/raw`: `message/rfc822` exact original MIME, full headers and signatures. Unknown/expired is `404` (B06).
- `GET .../{id}/attachments`; `GET .../{id}/attachments/{attachment_id}`: manifest and authenticated raw bytes (`application/octet-stream`); IDs `rea_...`; absent/expired `404` (B07).

`email.received` is a **metadata notification**, not the whole message. It carries `inbound_message_id`, addressing/subject/reply reference and authentication results; storage precedes event, so fetching body/raw immediately should work without polling (B04). Archive MIME, bytes and a hash before declaring business processing complete; acknowledge the signed notification after a durable intake record, then fetch asynchronously with retry (**proposed**). Reconciliation must list inbound mail even when no webhook exists. Keep overlapping received-time windows plus `rem_` dedup rather than treating one arrival-order cursor as a complete audit log.

**Coordinator correction after independent review I-01:** complete MIME does not reconstruct the
SMTP envelope. GET/LIST define `to`/`cc` as message-header recipients; a documented original
accepted-envelope-recipient field was not established. `inbound_address_id` filtering and nullable
`mailbox_id` are possible route evidence, not a proven mapping for arbitrary direct-domain aliases.
The pilot must use a separately provisioned receiving route whose server-side binding to one
company identity survives LIST backfill, or obtain a documented trusted envelope field. Missing
or contradictory route evidence holds/quarantines the message; never infer identity from visible
To. Test Bcc-only, mismatched headers, forwarding and two aliases. Bird is not declared incapable;
this portion remains conditional pending exact-contract and runtime proof.

Received mail including attachments has a 20 MB supported limit. Guide explicitly warns an oversized email is unsupported **even if the sender receives SMTP acceptance**; it may instead be rejected `552 5.3.4`; Bird says it never truncates to fit. Thus this cannot meet a literal requirement to capture every arbitrarily sized email. Document attachment-size boundaries in the support experience (B04).

Retention is 30 days for direct inbound and raw MIME. Optional mailboxes can extend retained extracted text/headers/attachments to plan-dependent 90/365 days, but original bodies and received raw MIME remain 30 days. Extracted text caps at 64 KiB and can omit content; old attachments can retain their original ~31-day expiry after a tier change. Do not use mailbox summaries as the authoritative original (B23).

Reply implementation (**proposed**): own stable From; choose destination from safely parsed inbound Reply-To/From under application policy; add `In-Reply-To` and bounded `References` using RFC IDs, not Bird IDs; explicitly set operational category and tracking policy; preserve the exact intended outbound content locally. Custom headers cap 25 and values 998 characters, CR/LF forbidden; long reference-chain behavior requires tests. `reply_to` supports 1–25 destinations. Outbound HTML/text each cap 524,288 characters; subject 998; 20 attachments; generated total 20 MB after base64 (raw files ~15 MB leaves little room). API does not accept a raw-MIME send field in the retained current schema. Inbound raw preservation does not imply outbound byte-for-byte passthrough (B02–B03).

**Sender trust warning:** `authentication` currently always `unknown`; `dmarc_pass` and `spam_score` always null. SPF/DKIM booleans exist but do not expose alignment/signing domains/selectors and do not prove the visible sender. A signed Bird webhook authenticates Bird's delivery, not a customer's refund authority. Provider-authenticated ingress and sender authentication are different hard gates (B04–B05).

## 5. Webhook authentication, retry and recovery

B08 documents:

- HTTPS public endpoint; `POST /v1/webhooks`; explicit catalog events (no wildcard); up to 100 types. Create returns `whsec_...` once.
- Headers `webhook-id`, `webhook-timestamp`, `webhook-signature`; HMAC-SHA256 over `{id}.{timestamp}.{raw-body}`, key from base64-decoded secret after stripping prefix. Verify raw bytes, reject timestamps beyond five minutes, constant-time compare, deduplicate stable `webhook-id`.
- At-least-once, no ordering. One JSON event per POST; 15-second response deadline; any `2xx` succeeds, all other responses/timeouts retry. Seven retries after initial attempt: 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h, ±20% jitter (~27.5 h). `429`/timeout raises sub-minute scheduled waits; bounded `Retry-After` extension.
- `POST /v1/webhooks/{id}/rotate-secret`: dual signing for 24 h, max five valid secrets.
- `GET /v1/webhooks/{id}/attempts`; `POST /v1/webhooks/{id}/replay`: failed deliveries only, not successful deliveries or events never attempted. Attempts retained three days; replay up to oldest 10,000 matching events, 20 jobs/org/UTC day, one redelivery attempt/event, `202` without job ID/count.
- Repeated failures degrade then auto-pause after about five days; owner email is rate-limited. Reactivation is manual/API; events while paused were never delivered and **cannot be replayed**. Replay while paused returns `202` but sends nothing. Deleting endpoint also kills outstanding retries.

Consequences (**inference**): signed durable intake plus independent inbound and outbound polling are mandatory. Three-day replay cannot cover an unattended long weekend reliably without monitoring. Event timestamps help ordering but do not imply simple irreversible status ranking: late out-of-band bounces can retract delivered status (B10). Message event `ev_` IDs and webhook delivery IDs are different identities; do not assume equality.

## 6. Outbound uncertain-send analysis — principal blocker

`POST /v1/email/messages` returns durable acceptance `202`, `em_` ID, aggregate recipient counts. Suppression is asynchronous: even every recipient suppressed can still produce `202`. An immediate GET may briefly return `404`, so absence immediately after sending does not prove non-acceptance (B02–B03).

Readback:

- `GET /v1/email/messages/{id}`: aggregate state, recipients/addressing, tags/metadata; no bodies.
- `GET .../{id}/recipients`: per-recipient outcomes; `er_` IDs.
- `GET .../{id}/events`: cursor timeline oldest first, optional `type`; `ev_` IDs, occurred_at, recipient ID, delivery/engagement/failure details (B10–B11).
- `GET .../{id}/content`: bodies up to 30 days **only if content storage enabled**; do not rely on provider for your outgoing audit record (B02).
- `GET /v1/email/messages`: tags, exact From/any To-CC-BCC, creation-time window, category, status, broadcast filters. Metadata is returned/echoed but **not a message-list search filter**. No documented list lookup by idempotency key or RFC Message-ID. Query parameters are strict (B01, B02, B11).

Use one unique operation tag (ASCII-safe <=64 characters) plus local operation ID in metadata to find accepted sends after losing `202` (**proposed**). Tags are recommended for low cardinality in docs, but the retained schema does not forbid operation IDs; test account indexing and high-cardinality behavior. A matching record proves acceptance; an empty eventually consistent list is not an authoritative proof that nothing was sent.

### Detailed idempotency contract takes precedence over summaries

B09 says optional key, nonempty <=255 characters, workspace-scoped, completed response retained **three hours**. Same key + identical request returns cached result with `Idempotency-Replay: true`; altered raw JSON whitespace/body/endpoint yields `409 E01005`; concurrent in-flight yields `409 E01004`, lock expires within 30 seconds. 4xx may be cached; 5xx never cached. `503 E01033` means this attempt did not execute, not that an earlier attempt did not execute.

Most importantly, B09 explicitly says: **“An operation can take effect before its response is retained; if that response is lost, or the in-flight lock expires, a retry can execute the operation again.”** This contradicts unconditional “retry safely” shorthand in sending/SDK guides. Treat this as a real send duplicate window unless Bird establishes a stronger email-specific atomic acceptance contract.

Current SDK automatically retries network errors/timeouts and transient HTTP failures twice, attaching the same generated key (B21). Therefore “we handle uncertain sends in our app” is insufficient if the SDK has already retried invisibly. **Proposed safety posture:** disable transport auto-retry for sends while atomicity is unresolved; persist frozen serialized request, deterministic key, operation tag and attempt record first; on uncertainty reconcile positive evidence; otherwise hold `unknown` for human decision, never silently resend after a deadline/expiry. This avoids deliberate second attempts but cannot guarantee eventual delivery. No local queue/lease transaction can make a remote non-atomic send atomic.

## 7. Suppression, events, unsubscribe, plan and rate gates

Current lifecycle includes accepted, processed, deferred, delivered, bounced, rejected, complained, late out-of-band bounce, opened/clicked and unsubscribe events. Delivery means remote mail-server acceptance, not inbox placement or reading. Tracking defaults **on**; explicitly choose otherwise for operational correspondence (B02, B10).

Hard bounce blocks all categories; complaint blocks non-transactional; manual suppression blocks all. New opt-outs are **Preferences**, not suppression records; marketing gets managed one-click headers and an in-body footer by default. Transactional does not get managed unsubscribe and is allowed through marketing-only opt-outs, but not all-message blocks. Classify honestly; do not label promotional support follow-ups transactional to bypass consent. Suppressions apply within minutes and do not stop already in-flight sends. Supabase must enforce its own immediate policy before submission and mirror both preferences and provider suppression state (B16–B17).

`GET /v1/email/suppressions?email=` is a **prefix**, case-insensitive lookup, not exact: paginate and compare full address; multiple reason rows may exist. Complaint removal requires signed-in human; service key receives `422`. Preferences reversal needs later `consented_at`, not deletion of a suppression (B16–B17).

Free documented plan: 1,000 monthly recipients, 50/day, one sending domain; no overage/card needed. Startup/Growth have variable allowances; dedicated IPs Growth+; Enterprise sales. Paid default overage ceiling five times included volume; actual limits must be read in chosen plan/account. Rate capacities are organization-wide across keys/workspaces; active override then plan value then default. Read effective `RateLimit-Policy` / `RateLimit`, honor `Retry-After`; an example `q=1000;w=60` is **not an account guarantee**. Increasing plan does not necessarily increase every rate. Billing/usage read not available to workspace keys (B13–B14, B18).

Unknown commercial gates: explicit inbound-message quota/price, minimum plan for own-domain inbound + raw retrieval, availability in newly provisioned legacy versus current workspaces, exact inbound read scope, content-storage enablement/default, retention of outbound states/events and indexing lag. Mailbox custom shared-domain handles and 90/365-day retention are paid allowances; not needed to justify direct inbound. Ask sales/support for these exact items, not “does Bird support email?” No requirement for enterprise sales to use the documented core API was found, but no actual signup entitlement was tested.

## 8. Legacy SparkPost: independently documented, not conflated

B15–B19 establish US/EU separate accounts and hosts, raw API-key auth, plan-dependent send caps (`420`), and:

- `POST /api/v1/inbound-domains`; MX `rx1/2/3.sparkpostmail.com` or `rx1/2/3.eu.sparkpostmail.com`, priority 10; Enterprise custom MX via TAM.
- `POST /api/v1/relay-webhooks`: match inbound domain, target, static `auth_token` sent as `X-MessageSystems-Webhook-Token`, or OAuth2 client credentials. Relay payload array `msys.relay_message` includes `content.email_rfc822`, `email_rfc822_is_base64`, parsed headers/text/html, `friendly_from`, envelope `msg_from`, `rcpt_to`. Attachments can be extracted from MIME (**inference**); no separate retained attachment API in the reviewed relay reference. GET relay-webhook retrieves **configuration**, not received mail.
- `POST /api/v1/transmissions`: inline recipients/Reply-To/custom headers/attachments or raw RFC822; content 20 MB; transmission ID and accepted/rejected counts. Current observed legacy reference **does document idempotency**: key `[A-Za-z0-9._-]{1,255}`, account/subaccount-scoped, 24 hours (scheduled: through 24 h after send), same-payload replay with `X-Idempotent-Replayed`, in-progress/different-payload 409. Do **not** repeat an older claim that SparkPost has no idempotency. Text claims exactly-once for replay; atomic crash persistence, availability across accounts, and retention-bound uncertainty remain untested.
- `GET /api/v1/events/message`: ten-day event retention, filters transmission/message/campaign/recipient/time. This is event search, not inbound-body recovery. Old Message Events API is explicitly deprecated/discontinued from 2019-10-01 (notice 2019-05-08).

**Unresolved blocker for choosing legacy instead:** relay-body retention, retrieval after webhook loss, authenticated replay and exact relay retry window were not established. Search finds eight-hour retry text for **Event Webhooks**; that is not proof of the **Relay Webhooks** contract and was deliberately not transferred. Support URLs can redirect into new Bird material too. Stronger legacy send replay wording alone does not establish all end-to-end hard gates or make legacy the preferred new integration.
